# 2026-09-07T190000Z — o comando documentado da CI escrevia bytecode; o `git add -A` do protocolo comitava-o

## Item

**Fora do backlog**, e a justificativa é que o achado não estava lá porque ninguém o tinha
procurado: `main` versionava dois arquivos de bytecode de Python, e o `.gitignore` não tinha regra
nenhuma para eles.

Cheguei aqui pelo passo 2 do protocolo. Ao medir a posse por arquivo dos 27 PRs abertos, três
deles (`#78`, `#79`, `#63`) apareciam a tocar caminhos `__pycache__/*.pyc` — o que não fazia
sentido para o que os seus títulos prometem. Não era intenção de ninguém: é o mecanismo.

O que se mede em dois comandos, nesta ordem:

```
$ python3 -m unittest discover -s tools/ci -p 'test_*.py'     # o comando que a CI documenta
Ran 12 tests ... OK
$ git status --short
?? tools/ci/__pycache__/
?? tools/profile/__pycache__/parse_metal_hud.cpython-311.pyc
?? tools/profile/__pycache__/test_parse_metal_hud.cpython-311.pyc
```

O passo 5 do protocolo do loop prescreve `git add -A && git commit`. A soma das duas coisas é
determinística: **quem roda o portão de CI e comita varre bytecode para dentro do commit sem ver.**
Foi assim que `tools/profile/__pycache__/*.cpython-314.pyc` chegou a `main` — bytecode de CPython
3.14, quando o interpretador desta sandbox e o da CI é o 3.11: o que estava versionado nem era
executável pelo ambiente que corre os testes.

Por que isto não é arrumação. `.pyc` é binário, e **binário o git não mescla**. Num repositório com
27 PRs abertos, cada cópia versionada é um conflito cuja resolução não tem significado — não existe
"escolher o bytecode certo", só existe regenerá-lo. E porque muda a cada execução em máquina
diferente, aparece como ruído em todo diff, num repositório cujo contrato inteiro é evidência.
É exatamente a entropia que o `CLAUDE.md` existe para conter, na sua forma mais barata de matar.

A guarda prova quatro coisas e recusa-se a provar uma quinta:

1. a regra existe e é **não ancorada** — sem `/` inicial e sem prefixo de pasta, que é o que a faz
   valer para `tools/ci/`, `tools/profile/` e para qualquer pasta de Python futura sem que ninguém
   se lembre de vir cá acrescentá-la (`tools/profile/` foi precisamente a que escapou);
2. há regra para a extensão solta, não só para o diretório;
3. nenhuma linha posterior desfaz a regra com negação (`!`) — no git a última regra que casa é a
   que decide, e uma negação distraída deixaria o `.gitignore` verde e inútil;
4. a varredura não é vazia: existem de facto ≥ 2 pastas com fonte Python sob `tools/`.

O que ela **não** prova, dito no cabeçalho do próprio teste: que não há `.pyc` versionado *neste
instante*. Um teste headless não consulta o índice do git, e `.pyc` em disco é legítimo — qualquer
execução dos testes de Python o recria. Aferir presença em disco deixaria a guarda vermelha por
motivo certo em hora errada. O que se defende é a **regra**, que foi o que faltou e cuja remoção é
a única forma de o problema voltar.
