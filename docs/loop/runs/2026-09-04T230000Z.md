## Por que este item passou à frente

18 PRs abertos, zero merges, `main` parado no commit de fundação desde 2026-09-03. Todo item de
P1, P2 e P3 do ledger herdado já tinha PR. Quatro execuções seguidas (#12, #14, #17, #18) já
tinham registado a saturação; abrir o 19.º PR de trabalho novo alimentaria o problema, e abrir o
5.º PR de registo não informaria nada que os quatro anteriores não digam.

O que faltava não era mais medição nem mais diagnóstico. Era o **artefacto que transforma 18
merges em um**.

## O que mudou

Esta branch é a fila **já integrada**: os 18 heads mesclados em sequência, cada um preservado como
ancestral por um commit de merge real. Mesclar esta branch em `main` torna os 18 ramos alcançáveis
a partir de `main`, e o GitHub marca #1–#18 como merged sozinho.

Além dos merges, dois arquivos são trabalho desta execução:

- **`docs/LOOP_LEDGER.md` — reescrito à mão.** Ver abaixo; é o achado principal.
- **`docs/loop/runs/2026-09-04T230000Z.md`** — este relato.

Nenhuma linha de `game/`, `ui/`, `app/`, `tools/`, `content/` ou `tests/` foi escrita aqui. O que
esta branch contém de código é exatamente o que os 18 PRs já continham.

## O achado: o código integra, a memória não

A ordem prescrita pelo #17 foi executada integralmente, com resolução automática por união para
conflitos em `.md` e falha ruidosa para qualquer conflito fora de `.md`:

```
#16 → #13 → #1 → #2 → #4 → #3 → #5 → #6 → #7 → #8 → #9 → #10 → #11 → #15 → #12 → #14 → #17 → #18
```

**Zero conflitos de código.** Dezasseis dos dezoito conflitaram só em `docs/LOOP_LEDGER.md`; três
deles também em `docs/TEST_MATRIX.md`. `#16` e `#18` entraram limpos.

E o `#8 × #11` **já não existe**: o patch que o #17 prescreveu foi aplicado pelo #18 na própria
branch do #8. A ressalva "aplicar o patch à mão senão a fila trava no #11" caducou — a sequência
fecha verde sem nenhum passo manual. Esse é o facto novo desta execução.

Mas a união automática, que passa nos testes, **corrompeu o ledger**. As 703 linhas resultantes
continham:

- cinco secções de "estado da fila" contraditórias, uma por execução, declarando 5, 7, 11, 13 e 16
  PRs abertos — todas simultaneamente presentes e todas falsas;
- três ordens de merge concorrentes, cada uma recomendando uma cabeça diferente;
- protocolo com dois passos `3`, dois `4` e três `5`, mutuamente inconsistentes;
- o mesmo item de backlog repetido até quatro vezes, em versões de datas diferentes.

Nada disso falha num teste. `doc_freshness_header_test.gd` só exige cabeçalho, e o cabeçalho
sobreviveu. **Um ledger assim passa verde e mente para a execução seguinte** — que é precisamente
o modo de falha que este arquivo existe para impedir.

Por isso o ledger foi reescrito à mão: backlog reconferido item a item contra o código integrado,
decisões fechadas unidas, notas de ambiente deduplicadas, histórico apontando para
`docs/loop/runs/`. A regra derivada disso está agora no protocolo do próprio ledger — *este
arquivo não se resolve por união automática*.
